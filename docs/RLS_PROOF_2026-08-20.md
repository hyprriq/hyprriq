## Result

**The anon surface leaks nothing. Cross-client isolation holds. One latent escalation found and
written up as describe-and-stop SQL** (`supabase/migrations/20260820000000_clients_self_no_role_escalation.sql`).

## What was tested, and how

### 1. The anon key — the surface an attacker actually has

`NEXT_PUBLIC_SUPABASE_ANON_KEY` ships to every browser. Straight at PostgREST, 16 checks:

| Check | Result |
|---|---|
| Read 14 client-carrying tables (`cases`, `clients`, `case_track_results`, `case_synthesis`, `case_outcomes`, `uploaded_files`, `reports`, `audit_log`, `case_prose_overrides`, `support_requests`, `case_evidence_packs`, `intelligence_events`, `billing_audit`, `admin_permissions`) | **200, rows=0 on every one** |
| `POST /cases` (create a case as anon) | **401** — `new row violates row-level security policy` |
| Header GUC injection (`app.current_user_id`, `X-App-Current-User-Id`) then read | **rows=0** — headers ignored |

Zero rows everywhere, not "the rows we expected" — anon cannot see a single client record.

### 2. Cross-client isolation — proven in-database

The GUC (`app.current_user_id`) is unreachable from client traffic, so this half cannot be driven
through PostgREST. Simulated with the real role and the real predicate, transaction rolled back:

```sql
set local role authenticated;
select set_config('app.current_user_id','user_3FUum7osm2AAO40gFPqixhC4jgh', true);  -- client B
```

| Measure | Value |
|---|---|
| Cases visible to B | **1** (their own) |
| **Cases belonging to client A visible to B** | **0** (A owns 38) |
| Client rows visible | 1 (self) |
| Synthesis rows visible | 0 |
| Audit rows visible | 0 |
| `is_current_user_admin()` | false |

**Case theft refused:** `update cases set client_id = <B> where client_id = <A>` → **0 rows**.

### 3. The finding — privilege escalation via the self-policy

`clients_self` was `FOR ALL USING (id = get_current_user_id())`, with no `WITH CHECK` and no column
restriction. `FOR ALL` includes UPDATE, and the row carries `role` / `is_admin` — the columns
`is_current_user_admin()` reads.

```sql
update clients set role='founder' where id='<own id>';   -- 1 row
select is_current_user_admin();                          -- true
-- then visible: 44 cases · 88 synthesis rows · 183 audit rows
```

**Not reachable today.** Nothing sets `app.current_user_id` for client traffic (no
`pgrst.db_pre_request` hook), so `get_current_user_id()` is NULL for every anon/authenticated
request and the policy grants nothing. An over-the-wire `PATCH clients?id=eq.<id>` with
`{"role":"founder"}` returned 204 having matched **zero rows** — verified against the row
afterwards: role is still `client`, untouched.

**It goes live the instant the Clerk→GUC wiring lands**, which is the obvious next step to make
these policies functional. Fix first, wire second.

## Standing note

RLS on the server path is defense-in-depth, not the primary control: `createServerClient()` uses
the service-role key, which **bypasses RLS by design**, and every server query scopes by hand
(`.eq("client_id", userId)`). This proof measures the depth behind that discipline — and confirms
that if the hand-scoping ever slipped, the anon surface still exposes nothing.

## Update 2026-08-20 (later) — escalation CLOSED, wiring decided

**The escalation fix landed and is independently re-verified** (in-DB, rolled back, nothing
changed): with `clients_self_update`'s WITH CHECK live, `update clients set role='founder'` as a
spoofed authenticated session is **REFUSED** ("new row violates row-level security policy"), a
legitimate self-edit still succeeds, and the target row's role is still `client`. `clients_self`
(blanket FOR ALL) is gone; `clients_self_read` (SELECT) + `clients_self_update` (UPDATE, power
columns frozen) replace it.

**The wiring is decided in [ADR-RLS-001](ADR-RLS-001-clerk-identity-wiring.md): a verified Clerk
JWT, not a settable GUC.** The naive "set the `app.current_user_id` GUC per request" reading is a
footgun over PostgREST's pooled connections — session-scope leaks across tenants, txn-scope never
reaches the query. Identity comes from `request.jwt.claims->>'sub'` after Clerk is registered as a
Supabase third-party auth provider; `get_current_user_id()` reads the verified claim first, GUC as
fallback (migration `20260820000100`, described-and-stopped, plpgsql exception-guarded so a
malformed claim can never take the portal down — proven live). Two founder-run dashboard steps
enable it; the RLS-scoped client + JWT adversarial probe land in that same session.
