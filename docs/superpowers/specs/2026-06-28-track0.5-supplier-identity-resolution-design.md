# Track 0.5 — Supplier Identity Resolution (Design Spec)

**Date:** 2026-06-28 · **Branch:** `staging` · **Status:** DRAFT — for founder review before any implementation plan.
**Proposed sequence slot:** **5.1c.5** — after Track 2 freezes, before 5.1d (Track 3), so Tracks 3–5 are built to consume the resolved identity natively and Tracks 1–2 retrofit onto it.
**Locked, do NOT touch:** ADR-G003/G004, `deriveTrackSignal`, `computeVerdict`, `weights.ts` scoring, the 6-gate firewall *logic*, the frozen Evidence Pack contract (`schema_version 1.0.0`).

## Why this exists (founder/CTO framing)
`vendor_website` is currently a hard, optional dependency: when a client leaves it blank, the engine silently loses
domain-age (Track 1) AND official-domain classification (Track 2 `official_company`) — degrading the verdict with no
signal to anyone. That's a hidden single-point-of-failure in the most-used input field. **Track 0.5 removes the
dependency:** it resolves the supplier's identity once — from whatever signals are available — into a
`SupplierIdentity` object that every track consumes instead of raw form fields. `vendor_website` becomes one
*high-confidence input among several*, never a precondition. The resolved identity also becomes the natural seed for
the Supplier Intelligence Profile (ADR-G006) — research compounds (the moat).

## Governing principle (LLM↔code boundary preserved)
**The LLM proposes candidate identities from research; deterministic CODE resolves the winner + confidence.** Same
boundary as the firewall. And the resolver is **conservative by design**: it only resolves a domain at high confidence
when signals strongly converge. When in doubt it resolves *nothing* (degrade gracefully, as today) and flags — because
the dangerous failure mode is the opposite of today's: resolving the **wrong** domain as official would poison Track 2's
`official_company`/`official_brand` trust signals. **Under-resolving (lose a benefit) beats over-resolving (false trust).**

## The contract — `SupplierIdentity`
Track 0.5 runs after Track 0, before the track fan-out, and writes `SupplierIdentity` onto the `TrackContext` that all
tracks read:
```ts
interface SupplierIdentity {
  resolved_name: string;            // canonical vendor name (from form, refined by research)
  resolved_domain: string | null;   // the vendor's own host → feeds vendorHost downstream; null if unresolved
  candidate_domains: string[];      // domains considered during resolution (audit)
  registration_signals: string[];   // lightweight business-registry hits found for the name (NOT a DUNS/VAT integration)
  identity_confidence: "high" | "medium" | "low";
  identity_unconfirmed: boolean;     // true when no confident resolution → caps the verdict
  resolution_method: "provided" | "resolved_dominant" | "ambiguous" | "unresolved";
  resolution_notes: string;          // human-readable why (analyst/audit)
}
```
Only `resolved_domain` (when confidence is high) populates the classification `vendorHost`. Brand domains stay derived
from the submitted brand names (Track 2 already does this) — Track 0.5 is about the **vendor's** identity, not brands.

## Resolution logic
1. **Website provided** → `resolved_domain` = its host; `resolution_method: "provided"`; `identity_confidence: "high"`.
   (Optional sanity cross-check: does the host's label relate to the vendor name? A mismatch lowers confidence + flags,
   never blocks.) This is the common, zero-research path — behaviorally identical to today when a website is given.
2. **Website absent** → run **identity-discovery research** (extends what Track 1 already does: business-registry,
   LinkedIn, address-verification queries on the name) → the LLM proposes candidate `{ domain, registration, address }`
   identities, each citing pack sources.
   - **One dominant candidate** (deterministic scorer below crosses the high-confidence threshold): resolve it →
     `resolution_method: "resolved_dominant"`, `identity_confidence: "high"`, `resolved_domain` set → feeds `vendorHost`.
   - **Multiple plausible distinct candidates, no clear winner:** `identity_confidence: "low"`,
     `identity_unconfirmed: true`, `resolved_domain: null` → **escalate, never guess** (handling = OQ-1).
   - **No candidate:** `resolution_method: "unresolved"`, `identity_confidence: "low"`, `resolved_domain: null` →
     proceed degraded (as today) + flag.

### Deterministic candidate scoring (code-owned IP)
A pure, deterministic scorer ranks candidates over convergent signals — e.g. name-token match between domain label and
vendor name, a business-registry hit, address consistency across sources, the domain self-identifying as the official
site. A candidate is **dominant** only if it clears an absolute threshold AND beats the runner-up by a margin (no
"least-bad guess"). Config lives in code (the `weights.ts`/`source_profile.ts` pattern), never an LLM or a UI.

## Integration
- **TrackContext** gains `supplier_identity: SupplierIdentity`. Tracks read `ctx.supplier_identity.resolved_domain` for
  the classification `vendorHost` (Track 2+) instead of raw `ctx.vendor_website`.
- **Track 1 (frozen) note:** switching Track 1 to consume `resolved_domain` is **behaviorally identical when a website
  was provided** (`resolved_domain` == the host) and **strictly additive when it was blank** (Track 1 gains domain-age
  it never had). So it's a safe retrofit — but it IS a frozen-contract input change → gets its own quick re-validation.
  Recommend: wire Track 2+ first (they need it now); retrofit Track 1 as a deliberate, re-validated follow-up.
- **vendor_website form field:** with Track 0.5 in place, the field can stay optional (the resolver handles blanks) —
  this supersedes the "make it required" question; required becomes a UX nicety, not an architectural necessity.

## Confidence → verdict handling
`identity_unconfirmed` (low confidence) must **cap the outcome** — you cannot deliver a confident verdict on an
unconfirmed supplier. Proposed: Track 0.5 escalates the case to `manual_review_required` (mirrors the existing
acquisition-failure guard), surfacing `candidate_domains` + `resolution_notes` for the human — rather than threading a
new signal into `computeVerdict` (keeps the locked verdict engine untouched). **OQ-1** decides ambiguity UX.

## Query set + prompt
Reuse the Orchestrator + a small Track-0.5 query set (vendor-name registry / official-site / address discovery — a
subset/extension of Track 1's queries) + an identity-resolution prompt (LLM proposes candidates with cited sources,
honest UNKNOWN). Mirrors the track pattern; no new infrastructure.

## Explicitly OUT of scope (deferred elsewhere, own future triggers)
- Document upload/parsing (invoices, POs, business cards, catalogs).
- DUNS / VAT / SEC registry integrations.
- Alibaba / Wholesale Central (or any marketplace) scraping.
- Client-facing disambiguation UI beyond what OQ-1 decides for v1.

## Determinism / locked guarantees
Track 0.5 is additive and upstream: it produces `SupplierIdentity` and improves the *inputs* tracks classify against —
it never touches `deriveTrackSignal`/`computeVerdict`/`weights.ts` scoring, the firewall logic, or the frozen pack
contract. The resolver is deterministic (LLM proposes, code decides). Conservative resolution prevents false official
classification.

## Testing (TDD, same discipline as the tracks)
Resolver unit tests: provided-website → high/provided; single dominant candidate → resolved_dominant/high; two
plausible candidates → ambiguous/low/unconfirmed (no domain); no candidate → unresolved/low. Conservatism: a weak
single candidate below threshold does NOT resolve. Integration: `resolved_domain` flows into the Track 2 classification
context → vendor's own pages classify `official_company`. End-to-end mocked; existing suite stays green.
