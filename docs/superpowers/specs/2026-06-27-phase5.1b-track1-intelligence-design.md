# Phase 5.1b — Track 1 Intelligence (design)

**Date:** 2026-06-27 · **Branch:** `staging` · **Builds on:** 5.1a (Evidence Pack contract FROZEN at
`schema_version 1.0.0`). **Locked, do NOT touch:** ADR-G003/G004/G005, `deriveTrackSignal`,
`computeVerdict`, `weights.ts` scoring, the frozen pack/provenance contracts.

**Goal:** Turn the frozen Evidence Pack into a scored Track 1 (Supplier Identity) signal — the LLM
*proposes* `weight_key` classifications from semantic understanding; a deterministic **five-gate
validation firewall** decides what actually scores; `deriveTrackSignal` (unchanged) scores only
validated evidence. Then run one real case end-to-end (acquire → interpret → validate → signal →
verdict → memory write).

## The LLM↔code boundary (founder-locked)
**The LLM never decides what counts. It proposes meaning; the platform decides what scores.**

```
Evidence Pack (frozen) → Track 1 LLM (proposes weight_keys + cites sources)
   → Weight Validation Firewall (5 deterministic gates) → validated weight_keys
   → deriveTrackSignal() [UNCHANGED] → track_verdict_signal → verdict + writeIntelligence
```

## Track 1 flow (replaces the `runTrack1` stub)
`lib/research/track1.ts` `runTrack1(ctx)` becomes:
1. Build the Track 1 acquisition request set (code-defined queries) → `Orchestrator.gather()` → pack.
2. Persist the pack + acquisition metrics (5.1a `persistEvidencePack` / `persistAcquisitionMetrics`).
3. Assign each pack source a stable `source_id` (index-based) for citation.
4. `runModel({ task: "track", system, user })` — the pack-interpretation prompt → JSON
   `{ evidence_items: [{ statement, proposed_weight_key, supporting_source_ids, certainty }], reasoning_notes, unknowns }`.
5. **Weight Validation Firewall** (below) → validated `EvidenceItem[]` (each with `weight_key` =
   validated key + provenance attached from its cited source) + a `WeightValidation[]` audit trail.
6. Return `TrackOutput` (existing contract) + the audit. The pipeline's existing
   `deriveTrackSignal(track_key, validatedWeightKeys)` scores it — no pipeline math change.

## The Weight Validation Firewall — `lib/research/weightValidation.ts`
Pure, deterministic. Input: proposed mappings (`{ evidence_id, proposed_weight_key, source }`) for a
track. Output: validated weight_keys + a `WeightValidation` record per proposal. Five named gates,
each emitting a distinct `rejection_reason` for the audit trail:

1. **Registry gate** — `weightFor(track, proposed_weight_key)` must be non-null. (This lookup is
   per-track, so it also enforces Gate 4.)
2. **Provenance gate** — the cited source's `source_profile` must be in
   `ALLOWED_PROFILES[weight_key]`. *(e.g. `government_registration` → only `government_record` /
   `registry`; a forum source is rejected.)*
3. **Authority gate** — the cited source's `authority_score` must meet `MIN_AUTHORITY[weight_key]`.
   *(Defense-in-depth; largely implied by Gate 2 since authority derives from profile — kept for an
   explicit, separate rejection_reason.)*
4. **Track compatibility gate** — the weight_key must belong to this track. *(Functionally the same
   per-track registry lookup as Gate 1; kept as a named check for audit clarity.)*
5. **Duplicate / contradiction gate** — dedupe identical mappings; resolve contradictions
   deterministically: (a) mutually-exclusive buckets (reuse `EVIDENCE_ALTERNATIVE_GROUPS`, e.g.
   `domain_age_5_plus` vs `domain_age_2_5`) → keep the highest-authority/most-specific; (b) a
   `hard_fail` key vs a positive key on the **same source** → the `hard_fail` wins (conservative).
   Code resolves — never the LLM.

### Gate config (code-owned tables, `lib/research/weightValidation.ts`)
- `ALLOWED_PROFILES: Record<string, SourceProfile[]>` — per Track 1 weight_key. e.g.
  `government_registration → [government_record, registry]`; `domain_age_* → [whois]`;
  `linkedin_company → [social]`; `bbb_or_trade_association → [registry]`;
  `scam_reports_corroborated → [forum, social, news, marketplace]`.
- `MIN_AUTHORITY: Record<string, AuthorityScore>` — e.g. `government_registration → high`,
  `linkedin_company → low`.
- Contradiction rules reuse `EVIDENCE_ALTERNATIVE_GROUPS` + a `hard_fail`-wins rule.
These are deterministic IP (code-only), same pattern as `weights.ts` / `source_profile.ts`.

### Audit persistence (respects locked contracts)
`WeightValidation = { evidence_id, proposed_weight_key, validated_weight_key: string | null, gate:
"registry"|"provenance"|"authority"|"track"|"contradiction" | null, rejection_reason: string | null }`.
Persisted to a new `case_track_results.weight_validation jsonb` column (founder-run migration).
`EvidenceItem.weight_key` (locked contract) stays = the **validated** key (or absent if rejected);
proposed/rejection live only in the audit structure. This makes systematic LLM misclassification
visible over time → data-driven prompt refinement.

## Track 1 query set — `lib/research/tracks/track1.queries.ts`
Code-defined `ResearchQuestion`s + query templates parameterized by vendor:
`domain_age` (host), `business_registry` (`{vendor} business registration`), `linkedin_presence`,
`bbb_listing`, `address_verification`, `scam_reports`. (The coverage lever; tracks 2–5 get their own.)

## Track 1 prompt — pack interpretation (not search)
System prompt: "You are a supplier-identity analyst. You are given an Evidence Pack of pre-collected
sources. Do NOT browse. For each finding, emit an evidence_item citing the supporting source_id(s),
propose ONE weight_key **from this exact list** [the ADR-G003 supplier_identity keys], and assign a
certainty. You PROPOSE classifications; the platform validates them." Output is structured JSON
(temp 0). The LLM cannot invent weight_keys (constrained to the enum) — and even if it does, the
firewall drops them.

## writeIntelligence integration
After the signal is derived, `writeIntelligence(ctx, signal)` records the real
`overall_risk_signal` on `vendor_intelligence` (5.1a already built the upsert).

## Determinism / locked-math guarantee
The firewall is **additive upstream** of `deriveTrackSignal` — it only *filters* which weight_keys
reach the unchanged scorer. All existing tests stay green; ADR-G003/G004 math is untouched.

## Testing

  `rejection_reason`: registry (unknown key), provenance (forum→government key), authority (low→high),
  track (cross-track key), contradiction (alt-bucket + hard_fail-wins). Dedup.
- `track1` evidence mapping — given a fixed model JSON + pack, produces validated `EvidenceItem[]`
  with provenance attached + the audit trail.
- Prompt-output parser — tolerant of malformed JSON (degrade to no-evidence, not crash).
- End-to-end (mocked providers + mocked model): pack → interpret → validate → `deriveTrackSignal`
  → signal; all existing tests green.
- Live validation: one real case through the real stack (founder-run via the pipeline / a dev route).
