# Phase 4.5 — Reasoning Transparency Layer (design)

**Date:** 2026-06-26 · **Branch:** `staging` · **Builds on:** Phase 4 (validated).
**Goal:** Make the deterministic engine explain *why* it concluded what it did — not just *what*.
Four explainers, all deterministic, all buildable on stub/seed data, all working identically once
Phase 5 supplies live evidence.

Scope (founder-locked): **items 1–4 only.**
1. **Confidence explanation** — why the decision/case confidence is what it is.
2. **"Why Not?" rejected-verdict reasoning** — for each unchosen verdict, why it wasn't reached.
3. **Evidence coverage** — how complete the research was.
4. **Missing evidence vs. unknowns** — expected-but-absent vs. looked-but-unresolvable.

**Deferred (unchanged):** item 5 decision-path visualization → post-Phase 5; item 6 engine
self-challenge → Phase 6 (it's a new LLM synthesis module, not a UX layer).

## Non-negotiable guardrail (single source of truth)
ADR-G004 logic lives in **exactly one place**. Items 1, 2 are powered by **extending
`computeVerdict()` to emit an additive `derivation` trace** — the UI/view model **never re-derives**
score thresholds, vetoes, or rejection logic. `VerdictResult` gains a `derivation` field; every
existing field is unchanged (additive, non-breaking). Items 3, 4 are pure aggregation over
`case_track_results` + the ADR-G003 weight registry, assembled in `buildVerdictViewModel()` (still
the only assembly service).

## Engine change — `lib/research/verdictEngine.ts`

`computeVerdict()` already computes everything needed; today it *discards* the intermediates. The
change is to **capture and return** them. New return shape: `VerdictResult & { derivation: VerdictDerivation }`.

```ts
interface TrackContribution {
  track_key: TrackKey; signal: TrackSignal;
  signal_score: number;   // SIGNAL_SCORE[signal]
  weight: number;         // TRACK_WEIGHTS[track_key]
  contribution: number;   // signal_score * weight (pre-redistribution)
  included: boolean;      // false if n_a / skipped (excluded from the score)
}
interface VetoStep { kind: "floor" | "lock"; verdict: Verdict; reason: string }
interface RejectedVerdict { verdict: Verdict; reason: string }

interface VerdictDerivation {
  contributions: TrackContribution[];
  total_weight: number; weighted_sum: number; raw_score: number; // 0–4
  thresholds: { source_clear: 3.2; usable_with_conditions: 2.2; verify_before_purchase: 1.2 };
  score_verdict: Verdict;            // verdict from score ALONE, before vetoes
  vetoes: VetoStep[];                // floors/locks that fired, in order
  final_differs_from_score: boolean; // true if a veto changed the outcome
  margin: { distance: number; nearest_boundary: number }; // drives decision_confidence
  rejected: RejectedVerdict[];       // the 3 unchosen verdicts + why (item 2)
}
```

**`rejected[]` logic (deterministic, item 2).** For the final verdict `F`, for each candidate `C ≠ F`:
- **C more favorable than F** (lower severity): reject reason combines (a) score gate —
  `raw_score` vs `C`'s threshold, and (b) any veto floor/lock that capped above it.
  e.g. final = Verify Before Purchase: *"Usable With Conditions — score qualified (2.40 ≥ 2.2) but
  floored by 2 load-bearing contradictions"*; *"Source Clear — score 2.40 below the 3.2 threshold."*
- **C less favorable than F** (higher severity): reject reason enumerates the absent triggers.
  e.g. *"Do Not Rely — no hard-fail veto, no critical contradiction, and score did not fall below 1.2."*

This is computed inside `computeVerdict` from the same thresholds/veto state it already evaluates —
no second encoding of ADR-G004.

## View-model change — `lib/research/verdictViewModel.ts`

`buildVerdictViewModel()` already calls `computeVerdict()`, so `derivation` arrives for free and is
exposed on the view model. Two new assembled sections (items 3, 4):

```ts
interface CertaintyBreakdown { verified: number; inferred: number; unknown: number }
interface EvidenceCoverage {
  tracks_run: number; tracks_skipped: number;          // vs plan
  total_evidence_items: number;
  certainty: CertaintyBreakdown;                        // across all evidence
  per_track: { track_key: TrackKey; dimension: string;
               evidence_count: number; certainty: CertaintyBreakdown;
               has_signal: boolean }[];
}
interface EvidenceGaps {
  per_track: { track_key: TrackKey; dimension: string;
               missing: { evidence_type: string; label: string }[]; // expected, not found
               unknowns: Unknown[] }[];                              // looked, unresolvable
}
```

`VerdictViewModel` gains `coverage: EvidenceCoverage` and `gaps: EvidenceGaps` (null when
`!engineComplete`). Both are pure helpers (`computeCoverage`, `computeGaps`) the assembler calls —
unit-testable in isolation.

### Item 4 design decision (the one judgment call — please confirm on review)
"**Missing evidence**" = ADR-G003 **positive-weight** evidence types for a track that were **not
found** (found = `weight_key`s present on that track's evidence items). This needs a small additive
export from `weights.ts`:
- `expectedEvidenceTypes(track)` → the positive-weight evidence_type keys for that track.
- `EVIDENCE_LABELS` → human labels (e.g. `invoice_full` → "Full wholesale invoice").

**Caveat I want your call on:** some expected types are *alternatives*, not all-required (a vendor
needs an invoice **or** an LOA, not both). A naïve set-difference over-reports "missing." My
recommendation: present `missing` as **informational** ("material evidence not found"), conservative
and explicitly *not* framed as "required" — so it reads as "here's what would have strengthened this,
and wasn't present," never as a checklist failure. Alternative if you prefer: curate a smaller
"material types" subset per track instead of all positive-weight types. Default = the conservative
informational framing.

> Note: `weight_key` tagging is fully populated only once Phase 5 tracks emit it; on seed scenarios
> it's present, so item 4 is demonstrable now and accurate on live data later.

## UI — `components/admin/case-review.tsx`

- **Item 1 (confidence explanation)** — folded into the **Verdict Panel**: a plain-language line
  under the scores, e.g. *"Decision confidence Low — weighted score 2.40 sits 0.20 from the Usable
  With Conditions threshold (2.2); a small evidence shift could flip the verdict."* Built from
  `derivation.margin` + `decision_confidence`.
- **Item 2 (Why Not?)** — a "Why not the other verdicts?" block in the Verdict Panel listing the 3
  `derivation.rejected[]` entries.
- **Items 3 + 4** — a new **"Research Coverage & Gaps"** section placed **after Track Intelligence**
  (it summarizes the evidence just shown): coverage counts + certainty mix + tracks run/skipped, and
  a two-column gaps view (**Missing** | **Unknowns**). Order is adjustable.

Engine Trace (collapsed) gains the raw `contributions[]` table (score math) for full auditability.
