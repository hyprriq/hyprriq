**Date:** 2026-06-28 · **Branch:** `staging` · **Builds on:** Track 1 (frozen) + Inngest durabilization (validated).
**Status:** DRAFT — for founder review before the implementation plan. No code yet.
**Locked, do NOT touch:** ADR-G003/G004, `deriveTrackSignal`, `computeVerdict`, `weights.ts` *scoring/weights*, the
6-gate firewall *logic* (`weightValidation.ts`), the frozen Evidence Pack contract (`schema_version 1.0.0`).

**Goal:** Make `runTrack2` real — interpret the frozen Evidence Pack into a scored Supply Chain Relationship

## ⚠ DISCREPANCIES vs the frozen code — REVIEW REQUIRED (read first)

The prompt's weight-key vocabulary does not match the actual frozen `weights.ts` registry. Taken literally, two of
these would **break the build** (the firewall's registry/track gates reject any key not in the registry, and
`deriveTrackSignal` scores only registry keys). I'm flagging + proposing reconciliations rather than building on them.

**D1 — Track 2 weight keys (build-breaking).** The prompt uses `brand_authorization_confirmed`,
`authorized_distributor_confirmed`, `reseller_certificate_present`, `b2b_only_brand_confirmed`, `grey_market_indicator`,
`no_authorization_evidence`. **None exist in `weights.ts`.** The *actual* frozen `supply_chain_relationship` registry
(10 keys, "do NOT modify") is:
`dealer_page_listed`(5), `loa_legitimate`(4), `invoice_matches_distributor`(3), `purchases_from_mega_distributor`(3),
`trade_press_connection`(2), `claims_authorization_unverified`(1), `no_connection_found`(0), `grey_market_signals`(−3),
`counterfeit_channel`(hard_fail), `conflicting_authorization`(hard_fail).
→ **Proposed reconciliation:** the LLM proposes these REAL keys; I map the prompt's intent + the master-spec Auth
Levels onto them (table below). This also matches `hyprriq_intelligence_engine_master.md` Part 2 (dealer-page/LOA = pass,
commercial distribution = infer, claims-unverified = flag, no-connection = soft_fail, conflicting/counterfeit =
hard_fail). The prompt's `ALLOWED_PROFILES` example keys are replaced with the real keys.

**D2 — `b2b_only_brand_confirmed` is not a Track 2 key.** The only B2B key is `b2b_only_confirmed` in
**`brand_risk_assessment` (Track 3)** (−5, hard_fail) — a *brand* signal, not a *supply-chain* one. There is no B2B
key in `supply_chain_relationship`. → **Proposed:** B2B-only is handled as **output metadata** (`b2b_only_detected`,
`b2b_only_brands`, surfaced in `reasoning_notes`) — NOT a Track 2 scored key. Absence of a reseller cert for a B2B
brand simply yields no positive key (Track 2 has no reseller-cert key to begin with), so B2B brands are not penalized.
This satisfies the prompt's intent without inventing a key. (Brand B2B *scoring* stays Track 3's job — 5.1d.)

**D3 — `EVIDENCE_ALTERNATIVE_GROUPS` lives in `weights.ts`, not `weightValidation.ts`** (line 126). The stacking-
prevention entry must be added there. → **Proposed:** treat "do NOT modify `weights.ts`" as *do not change weights/
scoring math*; **adding an alternative-group entry is additive config** (no weight/score changes), consistent with the
existing `domain_age` group. Flagging because it touches scoring *behavior* (see Open Question OQ-2).

## Auth Levels A–E → frozen registry keys → code-derived signal

The LLM never decides the signal. It proposes registry keys (per brand) + emits an **advisory** `auth_level`/reasoning
(like Track 1's `suggested_signal` — stored for QA, never scored). `deriveTrackSignal` (UNCHANGED) scores the
*validated* keys; the keys' existing points produce the signal the Auth Level implies:

| Auth Level | Meaning (master spec) | Proposed registry key(s) | pts | Code signal |
|---|---|---|---|---|
| A | On brand's official dealer page / official distributor page | `dealer_page_listed` | 5 | pass |
| C | Commercial distribution observable (mega-distributor / invoice / trade press) | `invoice_matches_distributor` / `purchases_from_mega_distributor` / `trade_press_connection` | 2–3 | infer |
| D | Claims authorization, unverifiable | `claims_authorization_unverified` | 1 | flag |
| E (absent) | No supply-chain evidence found | `no_connection_found` | 0 | soft_fail |
| E (conflicting) | Grey-market / counterfeit / contradictory | `grey_market_signals` (−3) · `counterfeit_channel` (hard_fail) · `conflicting_authorization` (hard_fail) | hard_fail | hard_fail |

**Level B (LOA) is intentionally removed (founder decision 2026-06-28 — revises master-spec Part 2).** HyprrIQ is a
**pre-purchase** tool; an LOA is post-relationship, privately issued, held by <10–20% of legitimate sellers, and not
independently verifiable. It is **not an authorization-discovery signal** — it belongs to a separate **Compliance
Documentation layer** (see below), not this engine. The pass path is Level-A publicly-verifiable indicators. The LLM
derives only the keys above (minus `loa_legitimate`); `auth_level` stays advisory (code derives the signal).

### LOA exclusion (load-bearing)
- `loa_legitimate` is **NOT** in Track 2's proposable key set (`SUPPLY_CHAIN_KEYS` = the 9 keys above). The LLM never
  proposes it; the prompt declares LOA out-of-scope for authorization.
- **Deterministic backstop:** `runTrack2` drops any validated `loa_legitimate` before scoring (code-decides — a rogue
  proposal can never score). Registry stays frozen; `loa_legitimate` remains a **Track 4 (documentation_review)** key.
- **Absence of an LOA is always neutral** — it was never scorable and never maps to `no_connection_found`.
- No Track 2 gate config for `loa_legitimate` (it's not proposable).

### Compliance Documentation layer (DEFERRED — not 5.1c)
Uploaded compliance documents (LOA, reseller certificate) belong to a separate Compliance Documentation module/report,
distinct from the authorization-discovery engine. Out of scope here; recorded as a future capability. (`reseller_certificate`
remains a Track 2 *public-discovery query* — a publicly-stated reseller relationship is fair authorization evidence; an
*uploaded* cert routes to Compliance, same as LOA.)

## Track 2 flow — `lib/research/track2.ts` (mirrors `runTrack1`)
1. `buildTrack2Requests(ctx)` → per (vendor × brand) queries → `Orchestrator.gather()` → pack.
2. Persist pack + acquisition metrics (5.1a).
3. Stable `src_i` ids; profile map for the firewall.
4. `runModel({task:"track"})` with the Track 2 pack-interpretation prompt → JSON (schema below).
5. **Reuse `validateWeights({ track: "supply_chain_relationship", … })`** — same 6 gates, Track 2 config. No firewall
   logic change.
6. Build validated `EvidenceItem[]` (each carrying `brand` + provenance) + `WeightValidation[]` audit + Track 2
   `track_validation_report`. Return `TrackOutput` (+ advisory `auth_level`, `b2b_only_*`, `questions_to_ask`).
7. Pipeline's existing `deriveTrackSignal("supply_chain_relationship", validatedKeys)` scores it — no pipeline math
   change. (Inngest `track-2` step already wired; registry entry already exists.)

## Brand isolation (every evidence item)
- Add additive `brand?: string` to `EvidenceItem` (Track 1 leaves it undefined — no impact).
- The prompt instructs: one source mentioning N brands → N evidence items, one per brand, all citing the same
  `source_id` (shared provenance, isolated brand attribution).
- Per-brand scoring is a 5.1c concern only for evidence attribution; `deriveTrackSignal` still scores the track's
  validated key set. (Per-brand *verdicts* are out of scope — deferred; see prompt "Deferred".)

## Authorization stacking prevention — SUPERSEDED (no group)
The original `[dealer_page_listed, loa_legitimate]` group is **dropped**: LOA is no longer scored (above), and among
the remaining public indicators none are mutually exclusive (a vendor can legitimately be on the dealer page AND buy
from a mega-distributor — both are genuine positive signal). **No Track 2 `EVIDENCE_ALTERNATIVE_GROUPS` entry.** (The
firewall's contradiction gate still resolves hard_fail-vs-positive same-source + equal-authority cases as for Track 1.)

## B2B-only archetype (output metadata, not scored — see D2)
Prompt surfaces `b2b_only_detected` + `b2b_only_brands` + an explicit note in `reasoning_notes`. No Track 2 weight key.
Absence of a reseller cert for a B2B brand → no negative key produced (and the prompt forbids inferring negatives from
absence). Drives a tailored `questions_to_ask` entry, not a score.

## Prompt — `lib/research/track2.prompt.ts` (pack-interpretation; mirrors Track 1)

prompt's brand-isolation, stacking, B2B-only, time-awareness (>3yr = historical in `mapping_justification`), UNKNOWN
("unknown ≠ negative"), and interpretation-boundary instructions. Per item: `brand`, `proposed_weight_key`,
`supporting_source_ids`, `mapping_justification`, `counter_evidence`, `certainty`, `confidence`.

`authorization_chain` surfaced if present but NOT persisted (deferred).

`parseTrack2Output` is tolerant (degrade to empty, never throw) — same as Track 1.
