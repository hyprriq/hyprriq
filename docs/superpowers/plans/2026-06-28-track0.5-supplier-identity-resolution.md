# Track 0.5 — Supplier Identity Resolution Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:subagent-driven-development (recommended) or superpowers:executing-plans. Steps use checkbox (`- [ ]`). **DO NOT START — awaiting founder review of this plan.**

**Goal:** Resolve the supplier's identity once — from `vendor_name` + optional `vendor_website` + (when needed) identity-discovery research — into a `SupplierIdentity` object that the tracks consume, so `vendor_website` is no longer a hard dependency for official-domain classification.

**Architecture:** A new pipeline stage `stageResolveIdentity` runs **after Track 0, before the finding-track fan-out**. The LLM proposes candidate identities from research; a **conservative deterministic resolver** (`identityResolver.ts`) decides the winner + confidence (under-resolve beats false official classification). The resolved `SupplierIdentity` is attached to the `TrackContext` the finding tracks receive; Track 2+ read `supplier_identity.resolved_domain` for the classification `vendorHost`. Low confidence → `identity_unconfirmed` → the case escalates to `manual_review_required` at finalize (computeVerdict stays locked). Decision logic, the firewall, and the frozen pack contract are untouched.

**Tech Stack:** TypeScript, Next.js 16, vitest, Supabase, Orchestrator + `runModel` (Sonnet 4.6, temp 0).

**Spec:** `docs/superpowers/specs/2026-06-28-track0.5-supplier-identity-resolution-design.md` + founder OQ answers (all approved as recommended): OQ-1 ambiguity → `manual_review_required` (client disambiguation deferred); OQ-2 wire Track 2+ now, retrofit Track 1 as fast follow; OQ-3 slot 5.1c.5; OQ-4 caps via escalation, not `computeVerdict`.

**Locked — do NOT touch:** `deriveTrackSignal`, `computeVerdict`, `weights.ts` scoring, the 6-gate firewall logic, the Evidence Pack contract. **Track 1 stays on `ctx.vendor_website`** this phase (retrofit is the OQ-2 fast follow). All 194 existing tests stay green.

## Task 3: Deterministic resolver — `identityResolver.ts` (the IP; TDD)
**Files:** Create `lib/research/identityResolver.ts` + `lib/research/identityResolver.test.ts`.

A proposed candidate carries code-derivable signals (the LLM proposes the candidate + cites sources; CODE sets the booleans):
```ts
export interface IdentityCandidate {
  domain: string | null;
  name_match: boolean;       // domain label matches a vendor-name token (code-derived)
  registry_hit: boolean;     // a cited source is registry/government_record profile
  address_consistent: boolean;
  self_identifies: boolean;  // a cited source on this domain is official_company-classified
}
export interface ResolveInput { vendor_name: string; vendor_website: string | null; candidates: IdentityCandidate[] }
```
Scoring (code-owned config; conservative): `score = name_match*2 + registry_hit*2 + self_identifies*2 + address_consistent*1`.
A candidate is **dominant** iff `top.score >= HIGH_THRESHOLD (4)` AND `top.score - runnerUp.score >= MARGIN (2)`.

- [ ] **Step 1: Failing tests** (`identityResolver.test.ts`):
```ts
import { describe, it, expect } from "vitest";
import { resolveIdentity } from "./identityResolver";

const cand = (domain: string, o: Partial<{ name_match: boolean; registry_hit: boolean; address_consistent: boolean; self_identifies: boolean }> = {}) =>
  ({ domain, name_match: false, registry_hit: false, address_consistent: false, self_identifies: false, ...o });

describe("resolveIdentity", () => {
  it("provided website → high confidence, method 'provided', resolved_domain = host", () => {
    const r = resolveIdentity({ vendor_name: "TD Synnex", vendor_website: "https://www.tdsynnex.com", candidates: [] });
    expect(r.resolution_method).toBe("provided");
    expect(r.identity_confidence).toBe("high");
    expect(r.resolved_domain).toBe("tdsynnex.com");
    expect(r.identity_unconfirmed).toBe(false);
  });
  it("one dominant candidate → resolved_dominant / high", () => {
    const r = resolveIdentity({ vendor_name: "Acme Distributing", vendor_website: null, candidates: [
      cand("acme-distributing.com", { name_match: true, registry_hit: true, self_identifies: true }),
      cand("acme-blog.net", {}),
    ] });
    expect(r.resolution_method).toBe("resolved_dominant");
    expect(r.identity_confidence).toBe("high");
    expect(r.resolved_domain).toBe("acme-distributing.com");
  });
  it("two plausible candidates, no clear winner → ambiguous / low / unconfirmed / no domain", () => {
    const r = resolveIdentity({ vendor_name: "Acme", vendor_website: null, candidates: [
      cand("acme-one.com", { name_match: true, registry_hit: true }),
      cand("acme-two.com", { name_match: true, registry_hit: true }),
    ] });
    expect(r.resolution_method).toBe("ambiguous");
    expect(r.identity_unconfirmed).toBe(true);
    expect(r.resolved_domain).toBeNull();
  });
  it("a single WEAK candidate below threshold does NOT resolve (conservative)", () => {
    const r = resolveIdentity({ vendor_name: "Acme", vendor_website: null, candidates: [cand("maybe-acme.com", { name_match: true })] });
    expect(r.resolved_domain).toBeNull();
    expect(r.identity_unconfirmed).toBe(true);
  });
  it("no candidates → unresolved / low / unconfirmed", () => {
    const r = resolveIdentity({ vendor_name: "Ghost Co", vendor_website: null, candidates: [] });
    expect(r.resolution_method).toBe("unresolved");
    expect(r.identity_unconfirmed).toBe(true);
  });
  it("typo on a dominant entity resolves silently — high, NOT ambiguity; original preserved (point 5)", () => {
    // "TD Synexx" (typo) → one dominant well-evidenced candidate. The fuzzy name-match (Task 6 signal
    // derivation) already absorbed the typo, so here name_match=true → dominant → high, no escalation.
    const r = resolveIdentity({ vendor_name: "TD Synexx", vendor_website: null, candidates: [
      cand("tdsynnex.com", { name_match: true, registry_hit: true, self_identifies: true, address_consistent: true }),
    ] });
    expect(r.identity_confidence).toBe("high");
    expect(r.identity_unconfirmed).toBe(false);
    expect(["normalized", "resolved_dominant"]).toContain(r.resolution_method);
    expect(r.original_input.name).toBe("TD Synexx"); // raw client input preserved regardless of resolution
  });
});
```
`resolveIdentity` MUST set `original_input = { name: vendor_name, website: vendor_website }` on every output (point 4).
`resolution_method: "normalized"` is used when a typo/alias/OCR variant resolved to a dominant entity (vs `"resolved_dominant"` for a clean dominant match) — both are high-confidence, neither escalates.
